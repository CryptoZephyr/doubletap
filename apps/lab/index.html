doubletap race lab

Two real races on Appwrite. Each button sends 100 requests at the same moment to two Appwrite Functions. One side uses the code most developers write. The other uses doubletap.

1. Someone taps Pay 100 times

Both functions ask "has this order been paid?" before charging. One checks and then writes. The other wraps the charge in doubletap.

Without doubletap

read order, if unpaid, charge

0 charges

0 of 100 requests finished

With doubletap

dt.once(orderId, charge)

0 charges

0 of 100 requests finished

Each line is one request, from when the function started to when it answered. it read the order and saw no charge. it charged the card. it got back the first charge instead of making a new one.

2. 100 workers grab the same job

A background job should run on exactly one worker. The left side uses an Appwrite transaction: read the job, and if nobody holds it, take it and commit. The right side uses a doubletap lease.

Appwrite transaction

read job, if free, take it, commit

0 workers own the job

0 of 100 workers finished

With doubletap

dt.lease(jobId)

0 workers own the job

0 of 100 workers finished

Each line is one worker. it committed and believes it owns the job. it was refused. More than one red dot on the left means two workers run the same job at once.
